# ADR-008: Lock the application row while checking INV-06

**Status:** Accepted

## Context

INV-06 says a request can only be created or approved when the mortgage application is OPEN.
The service read the application with a plain `findById` and checked the status. Applications
are reference data owned by the mortgage process, which may close one at any time by writing the
`mortgage_application` row directly. Between our status check and our commit, such a close could
commit, and the approval (or the new request) would be stored against a CLOSED application.
README "Before production" listed this as the known INV-06 race.

## Decision

- `MortgageApplicationRepository.findForUpdateById` reads the application with
  `@Lock(LockModeType.PESSIMISTIC_WRITE)`, which is `SELECT ... FOR UPDATE` on H2 and PostgreSQL.
- `PricingExceptionService` uses it at every INV-06 check: `create`, the APPROVED branch of
  `decide`, and `supersede`. The read-only approved-discount lookup keeps the plain read.
- The lock lives inside the service transaction only, never across HTTP calls (ADR-004 still holds).
- Nothing else changes: check order, error code `409 APPLICATION_NOT_OPEN`, messages, one event
  per status change.

A concurrent close now either commits before our locked read (we see CLOSED and reject) or waits
until our transaction has committed (the approval was stored while the application was OPEN).

## Consequences

Good:
- The INV-06 window is closed on both databases, proved by a test that holds an uncommitted close
  while an approval is sent.
- Creates and supersedes on the same application are serialised by the same lock, which also
  makes the INV-04 pre-check more reliable (the unique index remains the guarantee).

Bad:
- A writer that holds the application row open for a long time delays creates and approvals on
  that application until it commits. The lock is short-lived on our side.
- Lock waits are bounded by the database, not by us: no `jakarta.persistence.lock.timeout` hint
  is set. PostgreSQL waits until the other transaction ends (no `lock_timeout` by default). H2
  gives up after its `LOCK_TIMEOUT` (a few seconds by default) and the blocked call then fails
  with an unexpected-error response instead of waiting. Set a timeout per profile when the
  external writer is known to hold rows for long.
- An application row read for update that does not exist still gives `404 APPLICATION_NOT_FOUND`;
  no change for clients.
