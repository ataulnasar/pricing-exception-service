# ADR-002: Idempotency-Key on create and supersede

**Status:** Accepted

## Context

An upstream system may retry a call after a timeout. Without a key, a retry of a create gets
`409 ACTIVE_REQUEST_EXISTS` (INV-04), not the first response. The caller then cannot tell what
happened. See R5 in `docs/requirements.md`.

## Decision

- `POST` create and supersede accept an optional `Idempotency-Key` header (1 to 128 characters,
  scoped per caller).
- The first response (status, `Location`, `ETag`, body) is stored in the same transaction as the
  change.
- The same key with the same body replays the stored response with `Idempotent-Replayed: true`.
- The same key with a different body returns `422 IDEMPOTENCY_KEY_REUSED`.
- A key whose first request is still running returns `409 IDEMPOTENCY_IN_PROGRESS`.
- A failed request stores nothing.
- "Same body" means the same SHA-256 of a canonical form of the parsed body. Whitespace and field
  order do not matter.
- Records are purged after `pricing.idempotency.ttl` (default `PT24H`).

## Consequences

Good:
- A retry does not create a second request.
- The caller gets the same answer for the same key.

Bad:
- The `idempotency_record` table needs purging (hourly, see `docs/runbook.md`).
- The stored response must fit in `VARCHAR(16000)`.
- The caller must send the same values on a retry.

## Proved by

- `ConcurrencyIT.idempotent_parallel_creates_with_same_key_create_one_request_and_all_return_same_id`
- `ConcurrencyIT.idempotent_replay_returns_same_status_location_etag_and_body`
- `SupersedeIT.idempotent_supersede_replays_first_response`
