# ADR-003: One history event per status change

**Status:** Accepted

## Context

Users must see the full history of a request. A status with no matching history is a
compliance problem. See R4 in `docs/requirements.md` and INV-02.

## Decision

Every status change writes exactly one row in `request_event` (type, actor, time, from status,
to status, comment). The row is written in the same transaction as the status change. The
design says this table is insert only. Event types are `SUBMITTED`, `APPROVED`, `DECLINED`,
`WITHDRAWN` and `SUPERSEDED`.

## Consequences

Good:
- The history and the current status cannot be out of sync.
- The history gives a simple audit trail.

Bad:
- Each change writes one more row.
- Nothing in the database stops code from skipping an event. The tests prove it instead.

## Proved by

- `WorkflowIT.INV02_each_transition_writes_one_event`
- `ConcurrencyIT.INV02_losing_decision_writes_no_event`
