# ADR-007: Classic Spring MVC structure; business rules live in the service

**Status:** Accepted (supersedes the package layout described in ADR-006 and docs/design.md "Packages")

## Context

Phases 1 to 11 built the service with a separate `domain` package: one plain-Java aggregate
(`PricingExceptionRequest`) held every business rule, and a hand-written mapper copied it to and
from the JPA entity. The owner builds Spring MVC applications day to day and must explain and
defend this code in a technical interview. The extra layer was the one part of the code that did
not match the structure they know.

## Decision

The code uses the classic Spring MVC layout:

| package | holds |
|---|---|
| `controller` | `@RestController` classes and the `If-Match` parser |
| `service` | `@Service` classes: every business rule (INV-01 to INV-06), `@Transactional` use cases, idempotency |
| `repository` | Spring Data JPA repositories |
| `model` | `@Entity` classes, their enums (`RequestStatus`, `EventType`, `Role`, `ApplicationStatus`) and `Actor` |
| `dto` | request and response records |
| `exception` | `ApiProblem`, the business-rule exceptions and the `ProblemDetail` handler |
| `config` | the `Clock` and JSON beans, `pricing.*` properties, the `X-User-Id` argument resolver |

The `domain` package, the mapper and `reconstitute()` are removed. `PricingExceptionService`
works directly on the JPA entities. The checks on a decision keep their order (status, role,
self-review, approval limit, comment, then INV-06), their error codes and their messages. Every
status change goes through one private `transition` method that sets the status, sets or clears
`active_application_id` (INV-04) and appends exactly one `request_event` row (INV-02).

Nothing visible changes: URLs, status codes, error codes, headers (`ETag`, `Location`,
`If-Match`, `Idempotency-Key`, `Idempotent-Replayed`), JSON fields and the Flyway schema are the
same. The integration tests from before the change pass unedited except for package and import lines.

## Consequences

Good:
- The structure is the one most Spring developers expect, and the one the owner can explain.
- One class, `PricingExceptionService`, shows every rule and every state change.
- Fewer classes and no copying between an aggregate and an entity.

Bad:
- The rules are no longer testable without a database or mocks. The old plain-JUnit domain
  tests became service tests with mocked repositories and a fixed clock.
- The consistency checks that `reconstitute()` ran on every load (history starts with SUBMITTED,
  approved discount equals the discount, no decision fields on a PENDING row) are gone. The
  database constraints and the tests on the seed data cover part of this.
- ArchUnit can no longer forbid Spring and JPA imports in the rules; it now enforces the
  controller → service → repository direction instead, and that only `PricingExceptionService`
  calls a setter of the request entity (the structural side of INV-01).
- A stored row whose `active_application_id` disagrees with its status is no longer rejected on
  load; `PricingExceptionRequestRepositoryTest.INV04_every_stored_row_has_an_active_application_id_that_matches_its_status`
  checks every row instead.

## Proved by

- `PricingExceptionServiceTest` (the former domain tests, same `INVxx_` names)
- `ArchitectureRulesTest` (layering for the new packages)
- every `*IT` class: unchanged behaviour end to end
